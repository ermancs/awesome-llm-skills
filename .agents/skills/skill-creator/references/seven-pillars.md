## 1. Pushy description

**Failure it prevents:** *under-triggering*. Claude decides whether to consult a
skill from its `description` alone. A timid, purely-descriptive line ("Formats
data") loses to the model's instinct to just handle the task itself, so the
skill never fires when it should.

**The fix:** two clauses — *what it does* + *the specific contexts/phrasings that
should trigger it* — written to lean into triggering. Include casual wording,
near-synonyms, the user's own language (for Erman: Turkish **and** English
terms), and an explicit "even if they don't say the skill's name" nudge.

**Weak → strong:**

> ❌ `Builds a dashboard of internal metrics.`
>
> ✅ `Builds a fast dashboard for internal metrics. Make sure to use this
> whenever the user mentions dashboards, data visualization, internal metrics,
> KPIs, or wants to display any kind of company data — even if they don't
> explicitly say "dashboard".`

Pair the push with a one-line negative boundary so it doesn't over-fire (that's
pillar 7 leaking into the description, which is good — the router reads the
description first). Full craft notes: `description-guide.md`.

## 2. Progressive disclosure

**Failure it prevents:** *context bloat*. Everything in SKILL.md is loaded every
time the skill triggers. A 1,500-line SKILL.md burns budget on every invocation,
even when 90% is irrelevant to the current task.

**The three levels:**
1. **Metadata** (name + description) — always in context (~100 words).
2. **SKILL.md body** — loaded when the skill triggers. Keep under ~500 lines.
3. **Bundled resources** (`references/`, `scripts/`, `assets/`) — pulled in only
   when needed. Scripts can even *execute* without being read into context.

**The move:** keep SKILL.md to the workflow and decisions; push long tables,
per-variant docs, and deep domain knowledge into `references/*.md`, each behind a
one-line "read this when…". Files over ~300 lines get a table of contents so the
model can jump to the right section.

**Example — a multi-framework skill:**
```
cloud-deploy/
├── SKILL.md              # workflow + "pick your provider, then read its ref"
└── references/
    ├── aws.md            # read only for AWS deploys
    ├── gcp.md
    └── azure.md
```
The model reads `aws.md` for an AWS task and never loads gcp/azure — the whole
point.

## 3. Deterministic script

**Failure it prevents:** *re-derivation drift*. Without a bundled script, every
invocation re-writes the same helper (a CSV parser, a docx builder, a tax
calculation) from scratch — slower, and occasionally wrong in a new way each
time.

**The rule of thumb:** any step that is (a) repetitive, (b) error-prone by hand,
or (c) must be byte-identical every run belongs in `scripts/`. Prefer Python
standard library — Cowork has no network to `pip install` at runtime. The
SKILL.md says *when* to run it and with what args; the logic lives in the script
so it's written once and can't drift.

**Signal to bundle:** if you notice the model independently writing a
`build_chart.py` / `create_docx.py` in several test runs, that's the skill
telling you to bundle it.

**Example:** a "monthly-report" skill ships `scripts/render_report.py` that takes
a JSON of numbers and emits the exact formatted Markdown — so the arithmetic and
layout are identical whether it runs today or in six months.

## 4. CHANGELOG

**Failure it prevents:** *silent regressions*. Skills get iterated. Without a
record of what changed and why, you can't tell whether last week's edit helped or
hurt, and you can't cleanly revert.

**The format:** [Keep a Changelog](https://keepachangelog.com/) + semver. One
entry per meaningful change, grouped `Added / Changed / Fixed / Removed`, each
line carrying the *why*, not just the *what*.

**Example entry:**
```markdown
## [1.2.0] — 2026-05-14
### Changed
- Rewrote the trigger description to add Turkish phrasings after the skill
  under-fired on "sözleşme özetle" in testing (trigger rate 0.55 → 0.92).
### Fixed
- Report template was dropping the "Riskler" section when it was empty; now
  renders "Yok" so downstream parsing stays stable.
```

Gate each edit on an eval re-score (pillar 5): keep the change only if the skill
got strictly better, and record the delta here.

## 5. Eval

**Failure it prevents:** *blind, overfitted edits*. Without objective test cases
you're tuning on vibes, and a change that fixes one example often silently breaks
another.

**The shape:** 2–3 realistic prompts a real user would actually type (with the
user's real context — file names, column names, company names), each with
objective assertions where the output is verifiable. Subjective skills (writing
style, design) keep the prompts but grade qualitatively rather than forcing
brittle assertions.

**Division of labor:** the scaffold step (`new_skill.py`) just *seeds* the
`evals/evals.json` file with prompt + assertion stubs. The real work — with-skill
vs baseline runs, grading, the review viewer, and description-trigger
optimization — is the eval/benchmark loop documented later in this skill's main
SKILL.md. Fill in the stubs, then run that loop; don't reinvent it.

**Minimal `evals.json`:**
```json
{
  "skill_name": "sozlesme-ozetleyici",
  "evals": [
    {
      "id": 1,
      "prompt": "Ekteki kira sözleşmesini madde madde özetle, riskli maddeleri işaretle.",
      "expected_output": "Sectioned summary with a flagged-risks list.",
      "files": ["kira-sozlesmesi.pdf"],
      "assertions": [
        {"name": "has_risk_section", "text": "Output contains a 'Riskli Maddeler' section."}
      ]
    }
  ]
}
```

## 6. Templates

**Failure it prevents:** *format drift*. If the output shape lives only in the
model's head, every run reinvents it slightly — section order changes, a heading
disappears, downstream parsing breaks.

**The fix:** store the canonical output shape as an asset (`assets/templates/…`)
that the skill fills in. The structure is fixed; only the content varies. This is
what makes a skill's output feel consistent across a thousand invocations.

**Example:** a "meeting-recap" skill ships `assets/templates/recap.md` with fixed
`## Özet / ## Kararlar / ## Aksiyon Maddeleri` headings, so every recap has the
same skeleton no matter who ran it or when.

## 7. Scope guard

**Failure it prevents:** *mis-routing*. A well-triggering skill (pillar 1) will
also grab adjacent tasks that a sibling skill should own. Left unbounded, it
becomes a magnet that fires on near-misses.

**The fix:** a "When NOT to use this skill" section that names the sibling skills
owning adjacent tasks, and any hard boundaries (read-only built-ins, destructive
actions that need confirmation). The router reads this and sends edge cases to
the right place.

**Example:**
```markdown
## When NOT to use this skill
- Quick management of an installed skill (list / delete / validate) → use `skills`.
- "Which skill fits this request?" → use `skill-radar`.
- Built-in system skills are read-only — never scaffold over them.
```

A good scope guard is symmetric with the sibling skills' own guards: if A says
"for X use B", B should say "for Y use A". That mutual clarity is what keeps a
50-skill library from turning into a routing free-for-all.
